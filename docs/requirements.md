# 要件

依存の自動更新について、何を満たしたいかの一覧です。
どう実現するか、いまどこまで出来ているかは、ここには書きません。

## 目的

最高の Dependabot 運用を実現します。

- 運用全体が快適である。人の手間が小さい
- 安全である。壊れる更新や、悪意のある変更が入らない
- セキュリティに厳しい情報システム部門の担当者に、証拠を付けて説明できる
- チームのメンバーに、仕組みを一言で説明できる

規則を守ること自体は目的ではありません。運用全体が快適になるなら、二重管理のような妥協は許されます。

## 言葉の決め

「テスト」は、コードのテストと、本番のイメージの組み立ての両方を指します。組み立てたイメージを起動して確かめることは、求めません。

「変えられる」は、設定の変更か、コードの書き換えで変えられる、という意味です。

## 要件

| 番号 | 要件 |
|---|---|
| 1 | 自動でマージするか、人が判断するかは、semver で決める。patch は自動でマージする。minor は人が判断する。minor を自動にするかは、変えられる。major は人が判断する |
| 2 | 1 は、ライブラリにも、Python と Node の本体にも、同じように当てはめる |
| 3 | テストが落ちる更新は、自動でマージされない |
| 4 | ブランチが古いことを理由に、自動マージが止まらない |
| 5 | 自動でマージされる PR が、ひと目で見分けられる |
| 6 | 自動マージの仕組みを、人が自分の変更を通すために使えない |
| 7 | 人が判断する PR には、必ずレビュワーが付く。レビュワーは、CODEOWNERS の所有者か、それに類する関係者の中から、ランダムか、偏らない方法で選ぶ。何人に割り振るかは、変えられる |
| 8 | 使っているものの全部が、自動更新の対象になる。取りこぼしが無い |
| 9 | 通常の更新には、待つ期間（cooldown）を置く。セキュリティの修正には置かない。両者の違いは、これだけにする |
| 10 | 版の正本が、自然な場所にある |
| 11 | 手元、CI、本番のイメージで、Python、Node、uv の版が patch まで揃う |
| 12 | 同じ版を、人が複数の場所で管理しない。ふだんの更新で、人がファイルを手で編集しない |
| 13 | CI の費用が、無駄にかさまない。落ちたときに、原因を追いやすい |
| 14 | 情報システム部門の担当者に、証拠を付けて説明できる。GitHub App の作成を頼むための依頼書がある |
| 15 | 通知過多にならない。あるいは、通知を無視できる設定が個人に提供されていると好ましい |

## 対象にしないこと

- この仕組みを、ほかのリポジトリへ広げること
