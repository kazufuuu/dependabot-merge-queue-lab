# 要件

このリポジトリで実現したい依存の自動更新の、要件の一覧です。
何を満たしたいかだけを書きます。どう実現するかは書きません。実現の方法は README にあります。
状態の欄は 2026-11-15 時点のものです。

## 目的

最高の Dependabot 運用を実現します。次の 4 つを同時に満たすことを目指します。

- 運用全体が快適である。人の手間が小さい
- 安全である。壊れる更新や、悪意のある変更が入らない
- セキュリティに厳しい情報システム部門の担当者に、証拠を付けて説明できる
- チームのメンバーに、仕組みを一言で説明できる

規則を守ること自体は目的ではありません。運用全体が快適になるなら、二重管理のような妥協は許されます。

## 言葉の決め

「テスト」は、コードのテスト（単体テスト、lint、型検査）と、本番のイメージの組み立ての両方を指します。
本番のイメージの組み立ては、テストの一部です。組み立てたイメージを起動して確かめることは、行いません。

「切り替えられる」「変えられる」は、設定ファイルか workflow の実装を書き換えれば変えられる、という意味です。

## 自動マージ

| 番号 | 要件 | 状態 |
|---|---|---|
| A1 | 自動でマージする範囲は、semver で区切る。patch は自動でマージする。Python と Node の本体の patch も、同じ扱いにする | 一部。Python と Node の本体の patch は、自動でマージしていない |
| A2 | minor を自動にするかは、切り替えられる。最初は、自動でマージしない | 満たす |
| A2b | major は、自動でマージしない。切り替えでも自動にできない | 満たす |
| A3 | テストが落ちる更新は、自動でマージされない | 満たす |
| A4 | ブランチが古いことを理由に、自動マージが止まらない | 満たす |
| A5 | 自動でマージされる PR には、ラベルが付く | 満たす |
| A6 | 自動マージの仕組みを、人が自分の変更を通すために使えない | 満たす。一部の偽装は未試験 |

## 人のレビュー

| 番号 | 要件 | 状態 |
|---|---|---|
| R1 | 自動でマージされないものは、人がレビューする。major は、必ず人が判断する | 満たす |
| R2 | 人へのレビュー依頼が一切無い状態にはしない | 満たす |

| R5 | 何人に割り振るかを、変えられる。既定は 1 人 | 未試験 |

## 更新の対象と速さ

| 番号 | 要件 | 状態 |
|---|---|---|
| S1 | 使っているものの全部が、自動更新の対象になる。取りこぼしが無い | 満たす |
| S2 | 通常の更新には、待つ期間（cooldown）を置く | 一部。Python と Node の本体は、待たずに取り込んでいる |
| S3 | セキュリティの修正には、待つ期間を置かない。通常の更新との違いは、これだけにする。自動でマージするか人が見るかは、通常の更新と同じ線で決める | 一部。セキュリティの修正は、patch でも自動でマージしていない |
| S4 | Python と Node の本体も、同じ扱いにする。通常の更新は待ち、セキュリティの修正は待たない | 満たしていない。両者を見分けていない |

S1 の対象は、Python のライブラリ、npm のライブラリ、コンテナのベースイメージ、GitHub Actions、Terraform のプロバイダと本体、Python・Node・uv の本体です。

## 制約

実現の方法を選ぶときに、守ることです。

| 番号 | 制約 |
|---|---|
| K1 | 更新の道具は、当面 Dependabot にする |
| K2 | 仕組みは機械的な処理だけで組む。LLM を仕組みの中に入れない |
| K3 | ブランチが古くて止まる問題は、merge queue で解く |

## 決まっていないこと

- 複数人でのレビューの割り振りを、いつ実物で確かめるか

## 対象にしないこと

- この仕組みをほかのリポジトリへ広げること。予定が無い
- 更新の道具の乗り換え
