# 要件

このリポジトリで実現したい依存の自動更新の、要件の一覧です。
設計や実装を変えるときは、この一覧に照らして判断します。状態の欄は 2026-11-15 時点のものです。

## 目的

最高の Dependabot 運用を実現します。次の 4 つを同時に満たすことを目指します。

- 運用全体が快適である。人の手間が小さい
- 安全である。壊れる更新や、悪意のある変更が入らない
- セキュリティに厳しい情報システム部門の担当者に、証拠を付けて説明できる
- チームのメンバーに、仕組みを一言で説明できる

規則を守ること自体は目的ではありません。運用全体が快適になるなら、二重管理のような妥協は許されます。

## 言葉の決め

この文書で「テスト」と書くときは、次の全部を指します。本番のイメージの組み立てと起動の確認は、テストの一部です。

- コードのテスト（単体テスト、lint、型検査）
- 本番のイメージの組み立て
- 組み立てたイメージの起動の確認

## 自動マージ

| 番号 | 要件 | 状態 |
|---|---|---|
| A1 | 範囲は semver で区切る。patch は自動でマージする | 満たす |
| A2 | minor を自動にするかは、設定で切り替えられる。開発用の依存の minor から始められる | 満たす |
| A3 | テストが落ちる更新は、自動でマージされない。コードのテストは通るが本番のイメージが組み立てられない更新も、ここに含まれる | 満たす |
| A4 | 必須の検査は、テストの全部をまとめた 1 つにする。一部だけが通っても、マージされない | 満たす |
| A5 | マージは merge queue を通す。ブランチが古いことを理由に止まらない | 満たす |
| A6 | 自動マージを予約した PR には、ラベルを付ける | 満たす |
| A7 | 自動マージの仕組みを、人が自分の変更を通すために使えない | 満たす。一部の偽装は未試験 |

## 人のレビュー

| 番号 | 要件 | 状態 |
|---|---|---|
| R1 | minor と major は人が見る。人へのレビュー依頼が一切無い状態にはしない | 満たす |
| R2 | 自動マージされない PR には、必ずレビュワーが付く。放置される PR を出さない | 満たす |
| R3 | レビュワーは、CODEOWNERS の所有者の中から選ぶ。特定の人に偏らない。厳密なランダムでなくてよい | 設定済み。複数人では未試験 |
| R4 | 割り振る人数を変えられる。既定は 1 人、2 人にもできる | 設定済み。未試験 |
| R5 | すべてのファイルに所有者を付ける。所有者のレビューを免除するのは、自動マージ用の App だけ、ロックファイルだけにする | 試験中 |
| R6 | 更新の内容の判断と、落ちたテストの修正は、レビュワーが PR で行う | 満たす |

## 更新が届く範囲と速さ

| 番号 | 要件 | 状態 |
|---|---|---|
| S1 | 版の書かれた場所すべてに、更新が届く | 満たす |
| S2 | 脆弱性の修正の PR は、待たずに自動で出る。マージは人が行う | 満たす |
| S3 | Python と Node のセキュリティの修正に、速く追随する | PR は翌日までに出る |
| S4 | そのほかの更新は、公開から一定の日数を待ってから取り込む | 満たす |
| S5 | 待つ設定が効かない配布元を、気づかずに使わない | 満たす |

## 版の管理

| 番号 | 要件 | 状態 |
|---|---|---|
| V1 | 版の正本を、自然な場所に置く。Dockerfile を正本にしない | 満たす |
| V2 | 手元、CI、本番の Dockerfile で、版が揃う | Python と Node は満たす。uv は手元で下限まで |
| V3 | patch まで書いた版を置く場所は、対象ごとに最大 2 か所にする | 満たす |
| V4 | 正本への写しは機械が書く。ずれは検査が見つける | 満たす |
| V5 | ふだんの更新で、人がファイルを手で編集しない | 満たす |
| V6 | 人が意図して版を変えるときの手順が、短く決まっている | 満たす |

## CI

| 番号 | 要件 | 状態 |
|---|---|---|
| C1 | コードのテストは CI の上で直接動かす。コードのテストを Docker の組み立ての中で動かさない | 満たす |
| C2 | 本番のイメージの組み立てと起動の確認は、テストの一部として必ず動かす。依存の更新では省かない | 満たす |
| C3 | 落ちたときに、コードのテストとイメージのどちらが原因かをすぐ追える | 満たす |

## 仕組みの作り方

| 番号 | 要件 | 状態 |
|---|---|---|
| M1 | 更新の道具は、当面 Dependabot にする | 満たす |
| M2 | 仕組みは機械的な処理だけで組む。LLM を仕組みの中に入れない | 満たす |
| M3 | Dependabot が更新しない場所は、自前のスクリプトで補う。スクリプトは、決まった値を決まった場所に写すだけにする | 満たす |
| M4 | 回避のための仕掛けは少なく、種類も少なくする | 満たす |
| M5 | 鍵を持つ処理は、PR の中身を実行しない | 満たす |

## 説明と証拠

| 番号 | 要件 | 状態 |
|---|---|---|
| E1 | 主張には、実物で確かめた証拠を付ける。試していないことは、試していないと書く | 満たす |
| E2 | 情報システム部門に GitHub App の作成を頼むための依頼書がある | 満たす |
| E3 | 試してだめだった形と理由を、記録に残す | 満たす |
| E4 | 仕掛けの部品ごとに、何のためにあるかが書いてある | 満たす |

## 決まっていないこと

- 手元の uv を、patch まで厳密に揃えるか。揃えるには、版を管理する別の道具が要る
- Python と Node の patch を、人の承認を待たずにマージするか
- 複数人でのレビューの割り振りを、いつ実物で確かめるか。組織のメンバーが 1 人のため、今は確かめられない

## 対象にしないこと

- この仕組みをほかのリポジトリへ広げること。予定が無い
- 更新の道具の乗り換え。Dependabot で仕上げたあとに、必要なら改めて比べる
