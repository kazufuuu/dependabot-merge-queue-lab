# 要件

依存の自動更新について、何を満たしたいかの一覧です。
どう実現するか、いまどこまで出来ているかは、ここには書きません。

## 目的

最高の Dependabot 運用を実現します。

- 運用全体が快適である。人の手間が小さい
- 安全である。壊れる更新や、悪意のある変更が入らない
- セキュリティに厳しい情報システム部門の担当者に、証拠を付けて説明できる
- チームのメンバーに、仕組みを一言で説明できる

規則を守ること自体は目的ではありません。運用全体が快適になるなら、二重管理のような妥協は許されます。

## 言葉の決め

「テスト」は、コードのテストと、本番のイメージの組み立ての両方を指します。
本番のイメージの組み立ては、テストの一部です。組み立てたイメージを起動して確かめることは、求めません。

「変えられる」は、設定の変更か、コードの書き換えで変えられる、という意味です。「設定」には、コードの書き換えも含みます。

## 自動マージ

| 番号 | 要件 |
|---|---|
| A1 | 自動でマージする範囲は、semver で区切る |
| A2 | patch は、自動でマージする。Python と Node の本体の patch も同じ |
| A3 | minor を自動でマージするかは、変えられる。最初は、自動でマージしない |
| A4 | テストが落ちる更新は、自動でマージされない |
| A5 | ブランチが古いことを理由に、自動マージが止まらない |
| A6 | 自動でマージされる PR が、ひと目で見分けられる |
| A7 | 自動マージの仕組みを、人が自分の変更を通すために使えない |

## 人のレビュー

| 番号 | 要件 |
|---|---|
| R1 | 自動でマージされないものは、人がレビューする |
| R2 | major は、必ず人が判断する |
| R3 | 人へのレビュー依頼が一切無い状態にはしない |
| R4 | 自動でマージされない PR には、必ずレビュワーが付く |
| R5 | レビュワーは、CODEOWNERS の所有者か、それに類する関係者の中から選ぶ |
| R6 | レビュワーの選び方は、ランダムか、特定の人に偏らない方法にする |
| R7 | 何人に割り振るかを、変えられる。最初は 1 人 |

## 更新の対象と速さ

| 番号 | 要件 |
|---|---|
| S1 | 使っているものの全部が、自動更新の対象になる。取りこぼしが無い |
| S2 | 通常の更新には、待つ期間（cooldown）を置く |
| S3 | セキュリティの修正には、待つ期間を置かない。PR はすぐに出る |
| S4 | セキュリティの修正と通常の更新の違いは、待つ期間だけにする。自動でマージするか人が判断するかは、同じ線で決める |
| S5 | Python と Node の本体も、同じ扱いにする。通常の更新は待ち、セキュリティの修正は待たない |

S1 の対象は、Python のライブラリ、npm のライブラリ、コンテナのベースイメージ、GitHub Actions、Terraform のプロバイダと本体、Python・Node・uv の本体です。

## 版の管理

| 番号 | 要件 |
|---|---|
| V1 | 版の正本が、自然な場所にある |
| V2 | 手元、CI、本番のイメージで、版が patch まで揃う。Python、Node、uv のどれも同じ |
| V3 | 同じ版を、人が複数の場所で管理しない |
| V4 | ふだんの更新で、人がファイルを手で編集しない |

## CI

| 番号 | 要件 |
|---|---|
| C1 | CI の費用が、無駄にかさまない |
| C2 | CI が落ちたときに、原因を追いやすい |
| C3 | 本番のイメージが組み立てられることを、テストの一部として確かめる |

## 説明

| 番号 | 要件 |
|---|---|
| E1 | 情報システム部門の担当者に、証拠を付けて説明できる |
| E2 | 試していないことは、試していないと分かる |
| E3 | GitHub App の作成を情報システム部門に頼むための依頼書がある |
| E4 | チームのメンバーに、仕組みを一言で説明できる |

## 対象にしないこと
