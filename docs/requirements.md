# 要件

依存の自動更新について、何を満たしたいかの一覧です。
どう実現するか、いまどこまで出来ているかは、ここには書きません。

## 目的

最高の Dependabot 運用を実現します。

- 運用全体が快適である。人の手間が小さい
- 安全である。壊れる更新や、悪意のある変更が入らない
- セキュリティに厳しい情報システム部門の担当者に、証拠を付けて説明できる
- チームのメンバーに、仕組みを一言で説明できる

規則を守ること自体は目的ではありません。運用全体が快適になるなら、二重管理のような妥協は許されます。

## 言葉の決め

「テスト」は、コードのテストと、本番のイメージのビルドの両方を指します。ビルドしたイメージを起動して確かめることは、求めません。

「変えられる」は、設定の変更か、コードの書き換えで変えられる、という意味です。

## 要件

| 番号 | 要件 |
|---|---|
| 1 | ライブラリの更新を、自動でマージするか、人が判断するかは、semver で決める。patch は自動でマージする。minor は人が判断する。minor を自動にするかは、変えられる。major は人が判断する |
| 2 | Python のランタイムは patch の更新だけ、Node のランタイムは同じ major の中の更新だけ、PR を自動で出す。それより大きい更新は、人が時期を決めて上げる。Terraform 本体は、patch、minor、major のどれも、PR を自動で出す。これらの PR は、すべて人が判断する。uv は、ライブラリと同じ線で扱う |
| 3 | テストが落ちる更新は、自動でマージされない |
| 4 | ブランチが古いことを理由に、自動マージが止まらない |
| 5 | 自動でマージされる PR が、ひと目で見分けられる |
| 6 | 自動マージの仕組みを、人が自分の変更を通すために使えない |
| 7 | 人が判断する PR には、必ずレビュワーが付く。レビュワーは、CODEOWNERS の所有者か、それに類する関係者の中から、ランダムか、偏らない方法で選ぶ。何人に割り振るかは、変えられる |
| 8 | 使っているものの全部が、自動更新の対象になる。取りこぼしが無い。Python と Node のランタイムの大きい更新は、2 のとおり除く |
| 9 | 通常の更新には、cooldown を置く。セキュリティアップデートには置かない。両者の違いは、これだけにする。Python と Node のランタイムにも、同じように当てはめる |
| 10 | バージョンを、自然な場所で管理する |
| 11 | 手元、CI、本番のイメージで、Python と Node のバージョンが patch まで揃う。uv は、CI と本番のイメージで同じバージョンを使う。手元の uv は、古すぎなければよい |
| 12 | 同じバージョンを、人が複数の場所で管理しない。ふだんの更新で、人がファイルを手で編集しない |
| 13 | CI の費用が、無駄にかさまない。落ちたときに、原因を追いやすい |
| 14 | 情報システム部門の担当者に、証拠を付けて説明できる。GitHub App の作成を頼むための依頼書がある |
| 15 | 通知過多にならない。あるいは、通知を無視できる設定が個人に提供されていると好ましい |
| 16 | GitHub Actions のバージョン更新の PR は、週に 1 本とする。patch、minor、major を全部まとめる。自動でマージせず、人が判断する（GitHub Actions のバージョンは、ロックファイルと workflow 本体の両方にかかるため、自動マージの対象に指定しにくい） |
| 17 | PR にまとめるのは、バージョン管理が共通のライブラリ群だけにする |
| 18 | 本番のイメージをリリースするたびに、入っているもの（ベースイメージの OS のパッケージを含む）の一覧と、ビルドの来歴を、自動で作り、イメージと一緒に残す。脆弱性が見つかったとき、該当のバージョンがリリースしたものに入っているかを、すぐ調べられる |

## 対象にしないこと

- この仕組みを、ほかのリポジトリへ広げること
